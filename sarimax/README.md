# SARIMAX Models — Dengue & Chikungunya (State & Municipality Level)

Code in this folder fits, selects, and submits the SARIMAX models used for this challenge entry, at two geographic levels: state (all 27 UFs, the official IMDC submission level) and a fixed set of focal municipalities (`cities_dengue`/`cities_chikungunya` in `model_sel.r`, originally a supplementary/exploratory level; `sub_pred.r` can now submit either level -- see its entry below -- so whether a given run's municipality forecasts get submitted alongside the state ones is a per-run choice, not a pipeline limitation). State files come from `data_prep/agg_data_uf.r` (`processed_data/<disease>/<disease>_<UF>_agg.csv.gz`); municipality files live under `processed_data/<disease>/sel_cities/<disease>_<geocode>.csv.gz` and use IBGE geocodes as their identifier. `load_unit_data()` (`src/utils.r`) is what lets every other function treat both levels the same way -- see its entry below -- and writes everything under `sarimax/results/`, except the persistent covariate-forecast table, which lives under `processed_data/` alongside the disease/climate input tables it's built from (see `src/forecast_covariates.r` below).

## Files

| File | Role |
|---|---|
| `src/utils.r` | Shared library: `load_unit_data(disease, level, id)` (loads a state or municipality file and normalizes it to one canonical schema -- municipality files use "casos" instead of "cases" and lack the "_mean" suffix on weather variables like "temp_min" -- so every function below is completely level-agnostic and never branches on state vs. city itself), `fit_sarimax()` (unified core SARIMAX fit + forecast, used for all four validation splits and the submission window alike; forecasts its own regressors ex-ante via `forecast_covariates()` unless a precomputed `covariate_forecasts` matrix is supplied -- pass `table_path`/`id` to have it reuse the shared persistent covariate-forecast table described under `src/forecast_covariates.r` instead of always fitting live; before returning, calls `enforce_interval_nesting()` -- see "Predictive Uncertainty" in the root README -- to guarantee `pred` sits inside every interval and intervals nest from narrowest to widest, which `forecast()`'s bootstrap path doesn't guarantee on its own for low-signal units), covariate-selection helpers (`get_candidates()`, `filter_low_variance()`, `filter_by_correlation()`, `filter_redundant_indices()`, `select_best_per_variable()`, `build_covariate_combinations()`, `pca_all()`), the grid-search engine (`run_grid_search()` -- precomputes each fold's covariate forecasts once, up front, rather than once per formula/order combination, so that scoring every candidate under genuinely-forecasted covariates stays tractable; also accepts `table_path`/`id`), the scoring helper (`compute_metrics()`, computing WIS/MAE/RMSE/MAPE/coverage), and `read_leaderboard_csv()` (a thin `read_csv()` wrapper that forces the `formula_id` column to stay character -- an intercept-only formula's `formula_id` is the literal string `"1"`, and a column that's `"1"` or blank for every row of a unit type-guesses as numeric or logical on a plain `read_csv()`, silently corrupting it to `NA` once other units' formulas get `bind_rows()`-combined in; every read of a `metrics_all_formulas_*.csv`/`best_wis_*.csv` file, in this file, `model_sel.r`, and `fit.r`, goes through this helper instead of a bare `read_csv()`). Sourced by every other script. |
| `src/model_sel.r` | **Training / model selection.** Defines `run_model_selection(state=..., city=..., disease=...)` (mutually exclusive `state`/`city`; loads via `load_unit_data()`) and loops it over all states, then over the focal municipalities, for both diseases, writing per-unit CV metrics and `best_wis_<disease>_all_states.csv` / `best_wis_<disease>_all_cities.csv` summaries. Both of its `run_grid_search()` calls pass this unit's `table_path = covariate_forecast_table_path(disease, level)`, so its covariate forecasts are shared with `fit.r`/`evaluate_covariate_forecasts.r` (and a later re-run of model selection itself) instead of being re-fit from scratch each time. Before either `pca = TRUE` or `pca = FALSE` covariate selection proceeds, each base local-weather variable's lag/rolling family (contemporaneous plus `_lag4/8/12/16` and `_mean_3/6/9/12mo`) is collapsed to its single best-correlated-with-response variant via `select_best_per_variable()` -- both branches apply this same collapse now, so a variable's own mechanical transforms are never fed into PCA or the covariate-combination search as if they were independent variables. |
| `src/fit.r` | **Final fit & forecast generation.** `prepare_unit_covariates(data)` runs first for every unit: it filters candidate covariates (low-variance, then by correlation with the response) and, only if at least one non-ocean-index candidate survives, reduces them via `pca_all()`; if none survive (a real, if uncommon, outcome for a low-signal municipality), it returns the data unchanged and fitting proceeds covariate-free instead of calling `pca_all()` on an empty candidate set, which previously crashed inside `svd()` ("a dimension is zero"). `run_all_units(disease, level, target = NULL)` reads that (disease, level)'s `best_wis_..._all_<states\|cities>.csv` and calls `fit_unit_predictions()` once per unit (state or municipality) to refit the selected best model on the chosen train/target split(s) (via the shared `fit_sarimax()` in `utils.r`, passing this unit's persistent covariate-forecast table so root series `model_sel.r` already forecast for this exact unit/fold are reused rather than refit) and write one forecast CSV per unit x target window to `results/preds/`. `window_for_split()` resolves each split's train/forecast bounds: splits 1-4 are always the four fixed validation-test windows (never configurable), and `"forecast"` is the genuinely separate Forecast Phase window (`FORECAST_WINDOW`, from the config block at the top of the file, keyed only by `SUBMISSION_FORECAST_YEAR` -- see the root README's "Data Usage Restriction" section). `target` (and the `TARGET_TO_FIT` config constant right below that block, default `"validation"`) restricts which split(s) this run actually fits and (re)writes -- a split left out is neither fit nor touched, so an earlier run's CSV for it is untouched. It accepts a plain numeric subset of `c(1,2,3,4)` or, via `resolve_target_spec()`, a friendlier string: `"validation"` (all four), `"validation_1"`..`"validation_4"` (one split), or `"forecast"` (the Forecast Phase) -- e.g. `run_all_units("dengue", "state", "forecast")` fits and writes only `target_forecast.csv`. **Validation Test 4 and the Forecast Phase are two independent windows and two independent files** (`target_4.csv` vs. `target_forecast.csv`) -- fitting one never touches or overwrites the other, and both can exist on disk at the same time; they are not the same slot reused over time. At the bottom of the file, the driver runs `TARGET_TO_FIT` (default `"validation"`, all four splits) for every disease x level combination, THEN a separate additional pass with `target = "forecast"` for the same four combinations -- the second pass is preceded by `check_forecast_phase_data_ready()`, a one-time preflight check (against dengue/state/SP) that aborts with a clear error if `processed_data` doesn't yet cover FORECAST_WINDOW's train_end, rather than silently fitting every unit on fewer weeks of data than the window claims; it only guards the forecast-phase pass, never the validation pass above it. If a unit's chosen formula/order produces an actionable warning (a NaN standard error, an internal `auto.arima()` fallback, or an outright fit failure) on any split, `fit_unit_predictions()` retries with the next-best formula/order from that unit's full leaderboard (`metrics_all_formulas_<disease>_<id>.csv`) until a clean fit is found or the leaderboard is exhausted -- a single retry mechanism that now applies to every disease and level (previously this safeguard existed only for chikungunya states). A `(disease, level)` combination is skipped with a message, not an error, if that level's `best_wis_...csv` doesn't exist yet -- e.g. today, only the two state-level files exist, so the municipality calls are no-ops until `model_sel.r` has been run for cities. |
| `src/forecast_covariates.r` | **Covariate forecasting.** `forecast_covariates()` / `forecast_covariate_series()`, used by `fit_sarimax()` (and precomputed once per fold inside `run_grid_search()`) to produce genuine out-of-sample forecasts (not real future values, not a previous-year proxy) for every regressor the selected formula needs, for every validation split's own target window. Each root series is forecast with a 5-year seasonal ("epiweek-of-year") climatology: every future epiweek's forecast is the mean of that same calendar week across the most recent `n_years` (default 5) years of the series' own history -- pure base R, near-instant per series, and replaces an earlier `tbats()`/`stlf()`/`Arima()`-based approach that, at real-data scale, could take long enough per fit to starve other parallel workers of the table lock (see below). `parse_derived_covariate()` recognizes state-level lag/rolling columns (`<base>_lag4/8/12/16`, `<base>_mean_3/6/9/12mo`) as fixed transforms of one base series -- see `data_prep/agg_data_uf.r` -- so `forecast_covariates()` forecasts each distinct base series exactly once and mechanically re-derives its lag/rolling columns from that single forecast, rather than independently forecasting up to 9 columns that are mechanically one series. Also defines the **persistent covariate-forecast table**: `covariate_forecast_table_path(disease, level)` names one long-format CSV per (disease, level) at `processed_data/covariate_forecasts_<disease>_<state\|city>.csv` -- it lives there, not under `results/`, because once populated it's a precomputed input the modeling scripts just read, the same way they read the disease/climate tables under `processed_data/`. `get_or_compute_root_forecast()` -- used whenever `forecast_covariates()`/`fit_sarimax()`/`run_grid_search()` are called with `table_path`/`id` -- looks each base series' (unit, fold-window) forecast up there first (a fast, lock-free read), computing it outside any lock on a miss and only briefly acquiring the table's `dir.create()`-based file lock to re-check-and-write the result, so nothing is lost when multiple units finish at once and no worker holds the lock across a computation. Table writes are atomic (temp-file-then-rename) and reads tolerate a concurrently-in-progress write as a cache miss rather than erroring. **Known limitation:** the table's cache key is (unit, root series, fold window) only -- it does not fingerprint the underlying historical data, so if upstream weather/case data is corrected retroactively, already-cached rows are *not* automatically invalidated; delete the affected row(s) (or the whole table file) by hand to force a refresh after a real data correction. |
| `src/build_covariate_forecast_table.r` | **Bulk precompute utility (not part of the submission pipeline).** The persistent table above is normally filled lazily, as a side effect of running `model_sel.r`/`fit.r`/`evaluate_covariate_forecasts.r` -- this script instead warms it eagerly and exhaustively, up front. `build_covariate_forecast_table(disease, level)` forecasts every root covariate (the same 8 default candidates as `get_candidates(groups = "contemporaneous")`) for **every unit under `processed_data/`** (via `enumerate_processed_units()` -- every state/municipality file present, not just units that have already made it into a `best_wis_...csv` leaderboard) across all 4 validation splits, fanning out across a local PSOCK cluster by default (same `n_cores`/capping convention as `run_grid_search()`/`evaluate_all_units_covariate_forecasts()`). A unit/split combination that errors (e.g. a unit whose data doesn't cover that split's training window at all) is skipped with a message, not an error, so one bad task never aborts the run; the returned tibble's `ok` column records which tasks actually ran vs. were skipped. Run this once after a data refresh (or before a big batch of `model_sel.r`/`fit.r` runs) so every later covariate forecast in the pipeline is a pure table hit. |
| `processed_data/covariate_forecasts_<disease>_<state\|city>.csv` | The persistent covariate-forecast table (see `src/forecast_covariates.r` above): one row per (unit id, root covariate, fold train window, forecast step), shared by `model_sel.r`, `fit.r`, `evaluate_covariate_forecasts.r`, and `build_covariate_forecast_table.r` so a root series' forecast is computed at most once per (unit, fold). Lives alongside the other `processed_data/` input tables (not under `results/`), since it's a precomputed input the modeling scripts read, not a per-run output. |
| `src/evaluate_covariate_forecasts.r` | **Covariate-forecast diagnostics (not part of the submission pipeline).** Answers a separate question from the rest of this folder: how accurate are the covariate forecasts `forecast_covariates()` produces, really? `evaluate_unit_covariate_forecasts(disease, level, id)` re-runs `forecast_covariates()` exactly as `fit_sarimax()` would for each of the 4 validation splits (by default reusing the shared persistent covariate-forecast table -- pass `table_path = NULL` to force a fresh, uncached evaluation instead), then scores it against the real observed values already sitting in the processed data for whichever splits' target windows have already occurred (a split with no observed data yet -- e.g. split 4 before its season starts -- is skipped with a message, not an error); it reports MAE/RMSE/MAPE/bias/correlation per covariate, plus (by default) a naive seasonal-climatology baseline and a `skill_rmse` (positive means the covariate forecast beats climatology). `evaluate_all_units_covariate_forecasts(disease, level)` loops this over every unit in that level's `best_wis_...csv`, fanning units out across a local PSOCK cluster by default (`n_cores`, default `detectCores() - 1` capped at the number of units -- same pattern as `run_grid_search()`; pass `n_cores = 1` to force a plain sequential loop) since each unit alone is 4 splits x 8 covariates of climatology computation (though most of that is now typically a table hit rather than a fresh computation, once the table's been warmed), and writes `results/metrics/covariate_forecast_eval_<disease>_<state\|city>.csv`; `summarize_covariate_forecast_eval()` aggregates that into one row per covariate. Nothing here feeds back into `model_sel.r` or `fit.r`. |
| `src/sub_pred.r` | **Submission.** `submit_mosqlimate_forecasts(disease, level=..., ids=..., target=..., ...)` uploads the forecast CSVs in `results/preds/` to the Mosqlimate Predictions Registry via the `mosqlient` Python package (through `reticulate`), for either `level = "state"` (`adm_level = 1`, `adm_1` = UF code, `ids` defaults to all 27 UFs) or `level = "city"` (`adm_level = 2`, `adm_1` = the municipality's own state -- read from that unit's own case file's `uf_code`, same as the state path -- `adm_2` = the IBGE geocode, `ids` defaults to every municipality in `best_wis_<disease>_all_cities.csv`, the same leaderboard `fit.r`'s `run_all_units()` reads). Both levels share the same upload/duplicate-handling logic; only the case-file path convention and the `adm_1`/`adm_2`/`adm_level` triplet differ, mirrored via a small `resolve_case_file()` helper matching `load_unit_data()`'s two naming conventions. `target` (default NULL, meaning all four validation splits) uses the same `resolve_target_spec()` string vocabulary as `fit.r`'s `target`/`TARGET_TO_FIT` (a numeric subset of `c(1,2,3,4)`, `"validation"`, `"validation_1"`..`"validation_4"`, or `"forecast"`) to restrict which window(s) get submitted per unit -- e.g. `target = "forecast"` submits just the Forecast Phase, reading `..._target_forecast.csv` (a separate file from `..._target_4.csv`, Validation Test 4 -- submitting one never touches or duplicates the other), and auto-labels the upload description "final forecast" instead of "target_forecast" (override with `target_label`, which errors if given alongside more than one target). |
| `results/concluded_states_*.csv` / `results/concluded_cities_*.csv` | Checkpoints so `model_sel.r` can be safely interrupted and resumed without redoing finished states/municipalities. |
| `results/metrics/` | One `metrics_all_formulas_<disease>_<id>.csv` per unit/disease (every formula x order combination tried, ranked by mean CV metric; `id` is a UF code or a municipality geocode), plus `best_wis_<disease>_all_states.csv` / `best_wis_<disease>_all_cities.csv` (the winning combination per unit), `mean_wis_best_model_<disease>_<id>.csv` (final per-split metrics of the chosen model), and `resolved_formulas_<disease>_<state\|city>.csv` (written by `fit.r`, listing only the units where the top-ranked formula had to be retried against a lower-ranked one), and `covariate_forecast_eval_<disease>_<state\|city>.csv` (written by `evaluate_covariate_forecasts.r`, per-unit/split/covariate accuracy of the covariate forecasts themselves). If you read these files yourself rather than through `model_sel.r`/`fit.r`, use `read_leaderboard_csv()` (`src/utils.r`) instead of a plain `read_csv()` -- see its entry above -- so a unit whose `formula_id` is `"1"` (covariate-free) for every row isn't silently type-guessed to numeric or `NA`. |
| `results/preds/` | `pred_<disease>_<id>_target_<n>.csv` (validation splits 1-4) and `pred_<disease>_<id>_target_forecast.csv` (the separate Forecast Phase submission) — the actual forecast files (date, point prediction, and 50/80/90/95% interval bounds), ready to submit. `id` is a UF code for state-level forecasts or an IBGE geocode for municipality-level ones. `target_4` and `target_forecast` are independent files that never collide, even though both may be "the most recent forecast" at different points in the challenge calendar. Every row's bounds are guaranteed properly ordered and to contain `pred` (see `enforce_interval_nesting()` under `src/utils.r` above) -- a file generated before that guard existed can still have a stale, improperly-ordered row that the Mosqlimate submission API will reject; re-run `fit.r` for the affected unit to regenerate it. |

## How to run

From the repository root, with R and the packages listed in the root README's "Libraries and Dependencies" section installed:

```r
# Optional: eagerly precompute every root covariate forecast, for every unit
# under processed_data/, into the shared persistent table (see
# src/forecast_covariates.r / src/build_covariate_forecast_table.r below).
# Not required -- model_sel.r/fit.r/evaluate_covariate_forecasts.r fill the
# same table lazily on their own -- but useful to run once after a data
# refresh so every later covariate forecast is a pure table hit.
source("sarimax/src/build_covariate_forecast_table.r")

# Training / model selection for every state, then every focal municipality,
# both diseases. Long-running (grid search x ~26 states + ~15-25 cities x 2
# diseases). Safe to interrupt and re-run: already-finished units are skipped
# via results/concluded_states_*.csv / results/concluded_cities_*.csv.
source("sarimax/src/model_sel.r")

# Refit each unit's winning model and generate the 4 validation windows,
# for every (disease, level) combination that has a best_wis_...csv to
# read, THEN a separate additional pass fitting the Forecast Phase window
# (target_forecast.csv, independent of target_4.csv) for the same units --
# see "Data Usage Restriction" below and the config block at the top of
# fit.r.
source("sarimax/src/fit.r")

# Submit the forecasts to Mosqlimate (see "Credentials" below).
source("sarimax/src/sub_pred.r")
```

To experiment with a single state without running the full loop, call `run_model_selection()` directly after sourcing `src/utils.r` and `src/model_sel.r`'s function definition, e.g.:

```r
source("sarimax/src/utils.r")
source("sarimax/src/model_sel.r")  # defines run_model_selection(); the script's
                                    # own loop will also start running unless you
                                    # source only the function definition block
concluded_states <- data.frame(state = character(0))
result <- run_model_selection(state = "SP", concluded_states = concluded_states)
```

## Credentials for `sub_pred.r`

`sub_pred.r` never hardcodes the Mosqlimate API key. Create a `.env` file in the **repository root** (already excluded from Git via `.gitignore`) with:

```
MOSQLIMATE_API_KEY=your-key-here
```

Get your key from the "Auth" section of your Mosqlimate profile at [mosqlimate.org](https://mosqlimate.org/). Also update the `repository` and `commit` constants at the top of `sub_pred.r` to match the GitHub repository and commit hash you are actually submitting.

## Modeling summary

- Response: `log1p(cases)`, back-transformed with `expm1()` and clipped at zero.
- Covariates: PCA components of de-correlated weather variables, plus ENSO/IOD/PDO when they add signal beyond the retained weather components — see the root README's "Data and Variables" section for the full selection procedure. State files carry contemporaneous, lagged, and rolling-mean versions of each weather variable; municipality files only have the contemporaneous version (that feature engineering hasn't been done at municipality level upstream), so `get_candidates()` naturally draws from a smaller candidate set at that level -- this is a real difference in available signal, not something `load_unit_data()`'s schema normalization papers over.
- SARIMAX order: grid-searched per unit (state or municipality), bounded by `max_order` (default `p≤2, d≤1, q≤2, P≤1, D=0, Q≤1`), fit with `method = "CSS-ML"`, `optim.method = "BFGS"`.
- Selection metric: mean Weighted Interval Score (WIS) across 4 cross-validation splits (configurable via the `metric` argument of `run_model_selection()`).
- Prediction intervals: simulated (`bootstrap = TRUE`, `npaths = 1000`) at 50/80/90/95% coverage, with `enforce_interval_nesting()` guaranteeing `pred` sits inside every interval and intervals nest properly before anything is written to disk — see "Predictive Uncertainty" in the root README.

See the root `README.md` for the full Team, Data, Model Training, Data Usage Restriction, Predictive Uncertainty, and References sections required by the IMDC submission format.
